## 2025-02-27 - Mathematical Constant Inlining
**Learning:** In highly mathematical Python applications (like cosmology calculators running complex integrals), formulas often re-calculate constant coefficients from fixed physical constants on every function invocation. While Python scalar math is generally fast, eliminating these redundant operations via pre-calculation avoids implicit variable allocations and floating-point divisions, leading to measurable execution time reductions (e.g., ~16-20% speedup in tight loops or repeated calls).
**Action:** When auditing mathematical models or numerical integration fallbacks, analyze equations to factor out scalar constants (e.g., unit conversions combined with fixed fractional multipliers) and replace them with a single pre-calculated constant float value where safe.
## 2025-02-27 - Hoisting Loop-Invariant Scalar Calculations
**Learning:** In classes with methods called repeatedly (like optics or simulation samplers), calculating scalar constants involving multiple arithmetic operations and function calls (e.g., unit conversions) on every invocation introduces significant overhead.
**Action:** Identify loop-invariant scalar calculations and hoist them into the `__init__` method. Pre-calculating these values prevents redundant arithmetic overhead on every method invocation, yielding measurable speedups.
## 2025-03-02 - Hoisting Constant Arithmetic Expressions to Module Level
**Learning:** When attempting to optimize mathematical computations by pre-calculating constants (e.g., `4.0 * np.pi * sigma_sb`), replacing the expression with a hardcoded "magic" floating-point number (e.g., `7.12558509893708e-07`) destroys code readability and makes the codebase unmaintainable (especially for scientific values that might get updated in external libraries).
**Action:** Instead of hardcoding the result, hoist the exact mathematical expression to a module-level constant (e.g., `_STEFAN_BOLTZMANN_CONSTANT = 4.0 * np.pi * sigma_sb`). This allows the Python interpreter to evaluate the expression once at import time, eliminating redundant arithmetic overhead on every function invocation while fully preserving readability and correctness.
## 2026-03-05 - Avoid Generalized Power for Fractional Exponents
**Learning:** Using the generalized power operator (e.g., `x**-1.5`) in performance-critical mathematical paths introduces significant computational overhead compared to explicitly evaluating the equivalent expression using `math.sqrt` and basic arithmetic (`1.0 / (x * math.sqrt(x))`).
**Action:** Algebraically rewrite simple fractional powers to utilize explicit `math.sqrt` and arithmetic operations when executing loop-invariant or high-frequency scalar calculations.
## 2026-03-05 - Hoist Object Instantiation Outside Request Handlers
**Learning:** In Flask web APIs, instantiating complex classes (e.g., `Telescope` and `CCD` objects) inside the route handler causes them to be redundantly created from scratch on every single incoming API request. If these objects act as stateless configuration containers for methods, this introduces unnecessary memory allocation and CPU overhead.
**Action:** To provide a measurable performance improvement, hoist the initialization of static or stateless service objects outside the request handler to the module level. This caches the instances globally, drastically reducing execution time for the endpoint.
## 2026-03-05 - Avoid math.radians and math.degrees Function Calls
**Learning:** In performance-critical Python paths, converting angles using the built-in `math.radians(x)` or `math.degrees(x)` functions introduces significant function call overhead compared to multiplying by a pre-calculated scalar factor. In benchmarks, multiplying by `math.pi / 180.0` or `180.0 / math.pi` is roughly 3.8x faster than calling the respective built-in functions.
**Action:** When performing high-frequency angular conversions in scalar paths, hoist the constants `_DEG_TO_RAD = math.pi / 180.0` and `_RAD_TO_DEG = 180.0 / math.pi` to the module level and explicitly multiply by them instead of using `math.radians` or `math.degrees`.
## 2026-07-20 - Array Multiplication Optimization
**Learning:** In NumPy array operations, performing many consecutive in-place multiplications (e.g., `res *= wavelength` five times) involves multiple redundant array iteration passes, reading and writing large memory blocks repeatedly. Because NumPy is often memory-bandwidth bound rather than computationally bound, reducing the number of total passes yields a performance improvement.
**Action:** Identify sequences of repeated array multiplications and mathematically group them by pre-calculating intermediate squared or cubed arrays. Doing `w2 = w * w; res *= w2; res *= w2; res *= w` reduces the total number of element-wise array operations, providing a measurable execution speedup without sacrificing clarity.
## 2025-02-27 - Broadcasting and UFuncOutputCastingError
**Learning:** When applying native array operations in place of `np.empty(np.broadcast(a, b).shape)` blocks, doing `res += m` or `res *= arr` on two arrays that have different but broadcastable shapes (e.g. `(N, 1)` and `(1, M)`) causes a `UFuncOutputCastingError` or `ValueError` due to the output array `res` not matching the final broadcasted shape.
**Action:** When mixing NumPy arrays of different shapes, avoid in-place operations (e.g., `res += m` or `res *= arr`) to prevent broadcasting shape mismatch errors (e.g., 'non-broadcastable output operand'). Instead, use standard assignment (e.g., `res = res + m`) to allow NumPy to safely allocate a new array with the correctly broadcasted shape.
## 2026-07-25 - np.linspace and np.clip Dispatcher Overhead
**Learning:** In high-frequency loops (e.g., repeatedly generating simulated transit light curves), the generic dispatching and type-checking overhead inside NumPy functions like `np.linspace` and `np.clip` adds up significantly. `np.linspace` has substantial generic overhead compared to calculating the array using `np.arange` and applying step/offset arithmetic. Additionally, `np.clip` dispatches to the array method but adds measurable overhead.
**Action:** When a high-frequency function generates linearly spaced arrays or applies array bounds, replace `np.linspace` with an explicit `np.arange(points) * step - offset` equivalent, and replace `np.clip(arr, min, max)` with the direct `arr.clip(min, max)` method. This bypasses the dispatcher logic for substantial speedups without changing the output.
## 2026-10-09 - Fast-path Caching for Standard Mathematical Parameters
**Learning:** In mathematical utility functions that take physical parameters with standard defaults (e.g., standard cosmological parameters $H_0$, $\Omega_m$, $\Omega_\Lambda$), recalculating derived constants (like square roots and inverse hyperbolic functions of these parameters) on every invocation is computationally wasteful. While general caching (like `lru_cache`) helps, it doesn't eliminate overhead across changing non-cached inputs (like redshift $z$) when the cosmological parameters themselves remain static.
**Action:** To optimize mathematical utility functions that are called frequently with common default parameters, hoist the calculations for these specific defaults to module-level constants. Inside the function, add a fast-path check (e.g., `if param == _DEFAULT_PARAM:`) to return or use the pre-calculated constants, bypassing expensive floating-point and `math` operations on repeated calls.
## 2026-08-05 - Rate Limit Window Pruning Optimization
**Learning:** In highly trafficked API endpoints, keeping track of rate limits via a time window often involves pruning out-of-window requests on every call. If requests are appended chronologically, a standard list comprehension `[t for t in reqs if now - t < RATE_WINDOW]` still evaluates every element, turning it into an O(N) operation. As max request sizes grow, this limits the throughput severely.
**Action:** Replace the list comprehension with Python's built-in `bisect.bisect_right()` to perform a binary search in O(log N) time on the monotonically increasing timestamps list, yielding dramatic speedups (~20x faster) when slicing.
## 2026-08-13 - Parameterized Object Instantiation Caching in Request Handlers
**Learning:** While static service objects (like `Telescope` or `CCD`) can be hoisted directly to the module level to avoid redundant instantiation overhead per API request, objects whose configuration depends on request parameters (like `TransitSimulator(period_days=...)`) cannot. However, repeatedly instantiating these complex objects inside the route handler still incurs unnecessary CPU and memory allocation overhead.
**Action:** For complex objects parameterized by request inputs that are stateless after initialization, wrap their instantiation in an `@lru_cache(maxsize=128)` helper function at the module level. This caches the object instances across requests based on the input parameters, providing a measurable reduction in route execution time without compromising correctness.
## 2026-11-20 - Common Subexpression Elimination in Frequent Calculations
**Learning:** In frequently called mathematical methods (such as those computing metrics for plotting over arrays), redundant arithmetic calculations of invariant products introduce measurable overhead.
**Action:** Apply Common Subexpression Elimination (CSE) explicitly. If a product of constants (like `ZERO_MAG_FLUX * area * exposure * qe`) is already computed for one variable, reuse that variable instead of recalculating the entire product for another. Additionally, mathematically group terms with common multipliers (e.g. `(a * x) + (b * x)` -> `(a + b) * x`) to save operations, particularly when `x` is scalar. This yields significant speedups in tight loops without sacrificing clarity.
## 2026-11-21 - In-Place Scalar Multiplication on NumPy Arrays
**Learning:** When applying a scalar multiplier to the result of a NumPy function that creates a new array (e.g., `res = -2.17 * np.log(d)`), Python allocates one intermediate array for the result of `np.log(d)` and a second array for the final multiplication result. Because NumPy operations are often memory-bandwidth bound, this redundant allocation adds noticeable overhead.
**Action:** Eliminate the redundant array allocation by evaluating the array-creating function first (`res = np.log(d)`), then applying the scalar multiplication in-place on that new array (`res *= -2.17`). This avoids allocating the second intermediate array, yielding measurable speedups (e.g., ~16-20% for `absolute_magnitude`).
